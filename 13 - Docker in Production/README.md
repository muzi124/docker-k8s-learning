## 一、开篇核心思想

1. 遗留应用也可以容器化，**不必强行改成微服务**；12‑Factor 是努力目标，不要让理想阻碍容器落地。
2. 先分清哪些需求是必须、哪些是可选，循序渐进上生产。

## 二、Dockerfile 成熟度模型 & 反模式（重点）

### Dockerfile 成熟度递进

1. 能跑起来 → 日志输出到 stdout/stderr → 文件有文档说明 → 其他人也能构建成功 → 镜像精简 → 支持扩容伸缩

### 三大反模式（生产避坑）

1. **把持久数据存容器内部**
   - 问题：容器销毁数据丢失
   - 解决：使用`VOLUME`挂载持久化存储
2. **滥用 latest 标签**
   - 问题：`FROM latest`、安装软件包用 latest，构建结果不可控
   - 解决：基础镜像、关键软件包写死**具体版本号**
3. **直接使用程序默认配置，照搬虚拟机配置文件**
   - 示例：mysql、php、java 内存参数
   - 解决：通过`ENV`、`RUN`、`ENTRYPOINT`动态修改配置，适配容器环境

## 三、基础设施三大关键决策

1. **虚拟机上跑容器 vs 裸金属跑容器**
   - 两种都可以，优先选择自己熟悉的；做性能测试验证。
2. **操作系统、内核选择**
   - Docker 强依赖内核与存储驱动；“最低版本” 不等于 “最优版本”
   - 新手推荐 Ubuntu LTS；也可以使用 LinuxKit、InfraKit。
3. **基础镜像选择（FROM）**
   - 不要只看镜像大小；初期尽量匹配现有部署，后期再考虑 alpine 轻量镜像。

## 四、Swarm 集群生产架构方案（面试高频）

> 
> Swarm 依靠 Raft 共识，**管理器节点推荐奇数，保证仲裁 quorum**

1. **HA Swarm（3 节点，全部 manager）**
   - 最小高可用；允许**1 个 manager 节点故障**；适合测试、小项目、预算有限场景。
2. **Biz Swarm（5 节点，全部 manager）**
   - 商业生产最低标准；允许**2 个 manager 节点故障**，业务会产生金钱损失的环境优先选 5。
3. **Flexy Swarm（10 + 节点大规模）**
   - 固定**5 个专用 manager 节点**，其余全部作为 worker 业务节点；使用标签 + 约束控制容器调度；部分 worker 可放在 DMZ 隔离区。

> 
> 理念：不要把节点当宠物（pet），把节点当作牲畜（cattle），**假设节点随时会被替换，容器随时重建**。

### 多套 Swarm 集群：什么情况该多套集群

✅ **合理理由**：测试环境集群、地域隔离、权限管理边界
❌ **不应该拆分的理由**：仅仅硬件不同、子网不同、可用区不同，这些在一个集群内部就可以解决。

### Windows Server Swarm 建议

- 不建议纯 Windows 集群；**manager 尽量部署 Linux**；Windows 节点只跑 Windows 专属业务负载。

## 五、生产技术栈三套方案

1. **纯开源自建栈**
UI：Portainer；监控：Prometheus+Grafana；日志：ELK；七层代理：Traefik；镜像仓库：Docker‑distribution+Portus；编排：Docker Swarm；CI/CD：Jenkins。
2. **云托管简易栈（AWS/Azure）**
复用云厂商能力，镜像仓库使用 Docker Hub / Quay，降低运维负担。
3. **Docker 企业版 EE**
UCP 集群管理、DTR 企业镜像仓库；提供 RBAC 权限、镜像安全扫描、内容信任。

> 
> 思路：镜像仓库、日志、监控告警这类底层组件可以考虑外包 / 云服务，减少自建运维负担。

## 六、延伸方案：不一定非要上编排器

如果现有 VM 自动化、弹性伸缩已经很好，可以采用**一个 VM 内部跑一个容器**的折中方案：

- 改动小，依然使用 Dockerfile 管理应用，简化虚拟机镜像构建。
- 类似 Hyper‑V 容器、LinuxKit 不可变操作系统思想。
